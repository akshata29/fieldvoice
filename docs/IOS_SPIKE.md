# iOS: what is known, what is not, and the spike that settles it

About 80 % of the customer's future fleet is iOS. **Foundry Local does not run on iOS** (it targets Windows, macOS and
Linux), so the Windows demo does not carry over by itself. This page separates what was verified, what is reported but
unchecked, and what only a device test can answer - and defines a time-boxed spike to answer it.

Evidence labels: ✅ read from a primary source during this work · 🟡 reported by a secondary source / search summary -
verify before relying on it · ❓ not checked.

## What we know

| Fact | Evidence |
|---|---|
| ONNX Runtime **GenAI** (the engine inside Foundry Local, Windows ML and the VS Code AI Toolkit) lists iOS as **"on the roadmap"**; Objective-C API **"under development"**; Android and Windows/Linux/Mac are "supported now". Java needs a build from source. | ✅ [onnxruntime-genai README, support matrix](https://github.com/microsoft/onnxruntime-genai) |
| An **official iOS sample for Phi-3 exists**: an Objective-C++ wrapper over the GenAI C/C++ API with per-token timing (`LocalLLM`). So it can be built and run - it is just not a supported, packaged platform. | ✅ [onnxruntime-inference-examples/mobile/examples/phi-3/ios](https://github.com/microsoft/onnxruntime-inference-examples/tree/main/mobile/examples/phi-3/ios/LocalLLM) |
| A user reports **memory growth on iOS** when appending token sequences with ORT GenAI (v0.7.0 / v0.8.2; same code fine on Android). Open issue - exactly the kind of thing the spike must measure. | ✅ [onnxruntime-genai #1540](https://github.com/microsoft/onnxruntime-genai/issues/1540) |
| ONNX Runtime **core** has official iOS packages (Swift Package Manager `onnxruntime-swift-package-manager`, CocoaPods `onnxruntime-objc`). Any model that runs on core ORT (for example an ONNX Whisper graph) is therefore an iOS candidate without GenAI. | 🟡 [onnxruntime-swift-package-manager](https://github.com/microsoft/onnxruntime-swift-package-manager) |
| ORT GenAI exposes **Lark-grammar guidance** (`SetGuidance("lark_grammar", …)`) - the same mechanism the Python pipeline uses through Foundry. Whether guidance is compiled into an iOS build is unknown. | ✅ API in `ort_genai.h` · ❓ iOS build |
| Apple's **Foundation Models** framework (iOS 26+) gives an on-device ~3 B model with *guided generation* (`@Generable`) and no model distribution - but only on Apple-Intelligence-capable hardware (iPhone 15 Pro and later, M-series iPads). | 🟡 [Apple documentation](https://developer.apple.com/documentation/foundationmodels) |
| Apple's **SpeechAnalyzer / SpeechTranscriber** (iOS 26+) is a new on-device, long-form recognizer; the older `SFSpeechRecognizer` supports on-device mode (`requiresOnDeviceRecognition`) with shorter sessions. | 🟡 [SpeechAnalyzer](https://developer.apple.com/documentation/speech/speechanalyzer) |
| Azure *embedded* speech: Windows 11+ in the docs, access is gated, **no iOS**. Azure cloud speech obviously needs a connection. | ✅ earlier research, see [FINDINGS.md](FINDINGS.md) (row 8) |
| Whisper on iOS via Core ML / whisper.cpp / WhisperKit, and open LLMs via MLX Swift / llama.cpp / Core ML, are widely used. | ❓ not evaluated here |

## What ports and what does not

| Layer | iOS plan |
|---|---|
| **Contracts** (`backend/schemas`, REST/WS shapes, sync protocol) | Language-neutral JSON; reuse as-is. |
| **Deterministic core** (normalize → resolve → validate, form lexicon, prompts, grammars) | **Port to Swift.** It is dependency-free pure logic. `ios-spike/golden/golden_vectors.json` (generated by `python -m backend.evalkit.golden_vectors`, drift-checked by a test) is the conformance suite: normalizer tokens and offsets, rules-only field results with statuses, the real LLM prompts and grammars. |
| **LLM runner** | Interface (`LlmRunner`) with interchangeable backends - ORT GenAI iOS build, Apple Foundation Models, MLX/llama.cpp. The pipeline only needs "prompt + optional grammar → JSON text". |
| **STT runner** | Interface (`SpeechRunner`): Apple on-device, Whisper-family, ONNX/Core ML. |
| **Store + sync** | Reimplement against SQLite/Core Data with `URLSession`; the protocol (bundle hash, idempotent completions, `base_version` conflicts, outbox) is the contract in [SYSTEMS.md](SYSTEMS.md). Background sync needs iOS background tasks. |
| **UI** | Native SwiftUI, or the existing React app inside a `WKWebView` with the REST/WS transport replaced by a native bridge. Decide after the model spike; do not start here. |

## The spike (time-boxed; sized to the team, not guessed here)

**Inputs needed first:** the real device models in the fleet (chip and RAM decide everything; an iPad with 3 GB behaves
nothing like one with 8 GB), iOS versions, whether devices are MDM-managed, and whether Apple-Intelligence-class devices
are in scope.

1. **LLM feasibility** - build ONNX Runtime + GenAI for iOS (arm64), run the `ios-spike` benchmark with 2-3 int4 models
   (for example Qwen2.5-0.5B/1.5B and Phi-3.5-mini - ONNX exports of the same models Foundry Local serves on Windows) on the
   oldest and newest device. Record load time, TTFT, tokens/s, peak footprint, thermal state across 30 minutes of repeated
   runs, grammar-constrained vs unconstrained, and whether #1540-style memory growth appears. Optionally repeat with Apple
   Foundation Models and an MLX/llama.cpp model for comparison.
2. **STT feasibility** - Apple on-device recognizer (and SpeechAnalyzer on iOS 26) vs a Whisper-class model, on the synthetic
   audio *and* a handful of real recordings from the customer's environment.
3. **Core port** - implement `Normalizer` and the resolver in Swift against the golden vectors until every vector passes.
4. **End to end on device** - the work-order flow with the synthetic dataset subset; compare accuracy with the Windows run
   using identical metrics.

**Suggested decision gates** (agree them with the customer; these are starting points, not requirements):

| Gate | Starting value |
|---|---|
| p95 end-of-speech → proposed fields, on the **oldest** device | ≤ 5 s |
| Peak footprint while the app is foregrounded | well under the device's jetsam limit, no kill in a 30-minute loop |
| Thermal state during 10 consecutive extractions | never `serious`/`critical` |
| Valid-JSON rate with grammar guidance | ≥ 99 % |
| Field and identifier accuracy vs the Windows engines on the same cases | within an agreed margin |
| Silent-wrong rate | ≤ the Windows configuration |

**Outputs:** a `results-*.json` per run (schema `fieldvoice.ios-bench.v1`, written by the harness) summarized with the same
metric code as the Windows runs:

```bat
.venv\Scripts\python.exe -m backend.evalkit.ios_results results-llm-*.json results-stt-*.json --dataset synth-v1 --max-p95-ms 5000
```

It flags debug builds, low-power mode and thermal throttling, and scores speech with `wer_normalized` / `id_exact_match`.

## What is in `ios-spike/`

```
ios-spike/
  Package.swift                       SwiftPM library "SpikeKit" + tests
  Sources/SpikeKit/                   JSONValue, GoldenVectors, Results (schema), MemoryProbe (phys_footprint + peak sampler),
                                      Runners (LlmRunner / SpeechRunner protocols), LlmBench, SpeechBench, AppleSpeechRunner
  Tests/SpikeKitTests/                decodes the golden vectors; checks the results schema
  AppTemplate/                        SwiftUI harness + Objective-C++ ORT GenAI runner to drop into an Xcode app target
  golden/golden_vectors.json          conformance vectors (generated; the Python test suite fails if they drift)
```

> **None of the Swift / Objective-C++ code has been compiled or run** - there was no Mac in the environment that produced
> it. The call sequence in `OrtGenAIRunner.mm` follows the usage example in the current `ort_genai.h` and the official
> `LocalLLM` sample; header and library versions must come from the same build. Treat it as a head start, expect to fix
> compile errors, and do not quote any number from it until it has run on a device.
> The Python side (`golden_vectors`, `ios_results`) *is* tested.

## Risks to watch

* GenAI iOS is a self-built, unsupported configuration today (roadmap item): version pinning and CI for the build become
  our problem. Mitigation: keep the `LlmRunner` seam so a different backend can replace it.
* Memory: model weights + KV cache + the app on a small-RAM iPad; jetsam kills are silent. Test on the smallest device.
* Sustained load throttles phones and tablets; single-run benchmarks flatter them (the harness records thermal state).
* Apple Foundation Models and SpeechAnalyzer are attractive (no model distribution) but gate on OS version and hardware;
  they would split the product into "Apple-Intelligence devices" and "everything else".
* Constrained decoding may be missing from an iOS build; the pipeline already falls back from Lark grammar to JSON schema to
  none, and hybrid reviews every LLM suggestion - but accuracy and latency must be re-measured without it.
